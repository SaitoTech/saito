# Node development guidance

This file supplements [the repository guidance](../AGENTS.md) for `node/`.
Paths below are relative to this directory. Run the commands below from `node/`.

## Project map

- `mods/<module>/`: application modules and their local logic, UI, and assets.
- `lib/templates/`: framework templates, including the module integration base.
- `lib/saito/`: shared framework implementation and UI components.
- `web/`: shared browser assets; some files are generated by the build.
- `config/build/`: TypeScript and Webpack configuration.
- `config/modules.config.js`: configured server and browser module selection.
- `scripts/`: build, startup, and maintenance tools.
- `tests/`: Node tests; repository-level browser tests also live in `../e2e/`.
- `docs/` and module-local documentation: supplementary references whose APIs
  and examples should be checked against the current implementation.

## Implementation practices

- For module work, keep the normal scope within `mods/<module>/`. Identify any
  required shared framework or Rust/WASM change explicitly and explain why it is
  necessary for the task.
- Keep the main module as the map of framework integration and application
  coordination. Place substantial application logic and UI in meaningful local
  files, following the documented coding practices.
- Reuse appropriate Saito APIs and components. Check that an existing example
  reflects current guidance before copying its architecture or lifecycle behavior.
- For markup helpers, follow the `.template.js` convention and read the module
  requires guide before introducing asset imports. Webpack treats certain request
  strings, including `.html`, `.css`, and paths through `web/`, as externals.
- Edit source files rather than generated bundles or generated CSS. Check how the
  build produces a file before treating it as source.
- Preserve local configuration, wallet information, and chain state. A compile
  failure alone is not a reason to run a reset or reinitialize the environment.

## Commands and verification

Confirm command definitions in [package.json](package.json),
[scripts/compile](scripts/compile), and [jest.config.cjs](jest.config.cjs) when
working on the build or test setup.

| Purpose | Command / guidance |
| --- | --- |
| Run selected Jest specs | `npm test -- --runInBand --runTestsByPath tests/path/to/file.spec.ts` (replace the path with an existing matching spec) |
| Run configured Jest suite | `npm test -- --runInBand` |
| Compile browser assets in development mode | `npm run compile -- dev` |
| Start development server | `npm run dev` (long-running; inspect local configuration first) |

- Jest currently discovers `*.spec.ts` and `*.spec.js` under `tests/`; it excludes
  several archived specs. Files named `*.test.js` or tests elsewhere are not
  automatically covered by `npm test`. Inspect their runner and instructions.
- Use focused tests for the changed behavior. For browser changes, also verify
  the relevant UI or browser flow when possible; report when it was not exercised.
- Compilation regenerates module/shared CSS and browser outputs and can create
  missing local configuration files. Inspect the resulting diff for generated
  changes before including them in the task.
- Inspect the implementation and intended environment before using `nuke`,
  `reset`, setup commands, or scripts that invoke them. Do not use them as routine
  build/test prerequisites.
- Avoid repository-wide formatting for a localized edit. Follow neighboring style
  and limit any formatting command to the files being changed.
- Update relevant documentation when behavior or supported commands change;
  keep this file's reading routes and command guidance accurate.
